## 三策略综合方案（本日交付）

用户要求：在 app 内**同时实现**无障碍模拟点击 + DNS/Private DNS 过滤 + 本地 VPN 流量过滤；
本地 VPN 在非 VPN 使用时生效，**有其他 VPN 运行时让位**；定位个人/开源，暂不担法律风险。

- 新建 `reference/THREE_STRATEGY_PLAN.md`——三策略综合技术方案。

### 核心架构结论（重要）

**关键约束**：Android 官方明确规定「同一时刻只能有一个 VPN 连接运行，
新连接建立时旧连接被停用」，被抢占方收到 `onRevoke()`。
→ 因此 **S2(DNS) 与 S3(全流量) 必须设计为互斥模式，不能同时启用**。
  用 `NetworkFilterMode { OFF, DNS_ONLY, FULL_TRAFFIC }` 单开关控制。
→ 但 **S1(无障碍) 与 S2/S3 可同时开启**，因为无障碍服务不占用 VPN 资源。

**让位机制**（用户核心诉求）：
- 用 `NetworkCapabilities.hasTransport(TRANSPORT_VPN)` 检测其他 VPN（排除自身 handle）
- `onRevoke()` 中**绝不自动重连**——否则与其他 VPN 形成无限抢占循环
  （这是 Android 生态「VPN 反复掉线」的典型成因）
- 让位后在 UI 明示，恢复需用户显式触发，不做后台自动恢复

**S2 DNS-only 的精髓**：`VpnService.Builder` 只 `addRoute("10.0.0.1", 32)`
而不 `addRoute("0.0.0.0", 0)`，则仅 DNS 查询进 TUN，网页/下载/视频走原路径，性能影响极小。

**两个必须做对的细节**：
1. 上游 DNS 必须在 `establish()` **之前**读取，否则读到的是自己的虚拟 DNS（死循环）
2. 转发 socket 必须 `protect()`，否则 DNS 请求回流进自己 TUN

**S3 复杂度控制建议**：完整 TCP/UDP 转发是重型工程，建议先用「方案 C：域名级丢包」
（解析 DNS 得域名 → 命中黑名单则丢弃对应 IP 后续连接），避免自实现 TCP 栈。

## 新增：Shizuku 可选增强方案（本日交付）

用户追加提问：给 Shizuku 额外权限的手机能否做优化。交付
`reference/SHIZUKU_ENHANCEMENT.md`。

### 调研确认的 Shizuku 事实（已核实）

- 原理：用户一次 ADB 启动 Shizuku Server（**UID 2000 shell**，非 root）；
  App 通过 `ShizukuBinderWrapper` 把系统 API 调用转发给 Server 执行。
- **边界**：重启后失效；不能授予 `dangerous` 权限（`pm grant` 无效）；
  不能读其他 App 沙盒；普通 App 进程内仍受 Hidden API 限制；
  shell 权限随 Android 版本 / 厂商 ROM 漂移。
- 官方已明确 **`newProcess` 将被移除，应改用 `UserService`**
  （newProcess 走文本通信，低效且不可靠）。
- `UserService`：在独立进程运行自有代码，UID 2000（ADB）/ 0（root），
  不受非 SDK 接口限制，适合长驻状态与重复 Binder 调用。

### ⭐ 最重要发现：Chain-3 绕过 VPN 互斥

`ShizuWall`（开源，无需 root）已验证：通过 Shizuku 调用 connectivity 服务的
**Chain-3 接口**，可按包名切断联网，**不建 TUN、不占 VPN、可与其他 VPN 共存**。

**这直接解决了主体方案最硬的约束**（S2/S3 因单一 VPN 限制而互斥）。
据此新增「**S4 应用级断网（APP_FIREWALL）**」模式，并让 `VpnArbitrator`
在检测到其他 VPN 时**从「完全让位」升级为「降级到 S4」**。

### 文档覆盖的 6 项优化

| 优化 | 价值 |
|---|---|
| Chain-3 单应用断网 | 🔴🔴 架构级，解决 VPN 互斥与让位后失效 |
| Private DNS 直接改写（`WRITE_SECURE_SETTINGS`） | 🔴🔴 零代码替代 S2，不占 VPN |
| 绕过 Android 13+ 侧载受限设置 | 🔴 侧载必遇问题，体验提升大 |
| 冻结/隐藏/组件停用（`setComponentEnabledSetting`） | 🟡 根治开屏广告（S1 只能等它出现再点） |
| AppOps 权限拒绝 | 🟡 削弱广告 SDK 保活/悬浮窗/设备标识 |
| `forceStopPackage` 强制停止 | 🟡 S1 兜底，但风险最高，建议默认关闭 |

### 设计原则（已写入文档）

1. **Shizuku 是可选增强，不是前提** —— 无 Shizuku 设备核心功能必须完整可用。
2. 每项能力**独立运行时探测 + 独立降级**，不做「有 Shizuku 就有一切」的静态假设。
3. 增强项**默认全部关闭**，由用户显式开启，UI 如实标注状态。
4. `core/shizuku` 只被 Service/Repository 层引用，禁止 `feature/` 直接调用。

## 关键实现决策

1. **手写依赖容器**（`AppContainer`，全 `lazy`）而非引入 Hilt/Koin ——
   单模块、依赖图浅，DI 框架的注解处理收益不划算。
   已记录：ViewModel 超过约 15 个时应重新评估。
2. **领域模型不依赖 Room 注解**，转换集中在 `Mappers.kt`。
3. **枚举以 String 存库**（非序号），避免枚举增删导致存量数据错位。
4. **主键/索引按热路径设计**：`skip_rule.package_name` 建索引（S1 每事件都要按包名取规则）；
   `domain_rule.pattern+is_whitelist` 唯一索引（防重复导入）；`intercept_log.timestamp` 索引。
5. **`DomainRuleEngine` 不可变 + 预编译哈希集合**：匹配为 O(域名层级数)，
   可被 S2 包处理线程与 S3 转发线程无锁并发读取；
   规则变更时由 Repository 重建实例整体替换（Mutex 串行化写路径）。
6. **后缀匹配正确实现**：逐级剥离子域（`a.b.example.com` → `b.example.com` → `example.com`），
   而非 `endsWith` —— 后者会让 `badexample.com` 命中 `example.com`。
7. **应用管理语义**：开关关闭 = **删除**纳管记录，而非置 enabled=false，
   使「受保护应用数」语义清晰。
8. **UI 重构**：首页新增「三策略状态」列表（如实标注未生效原因而非笼统显示"已保护"）；
   网络页把互斥约束表达为**单选分组**（从交互层杜绝冲突配置），
   并明确标注每种模式是否占用 VPN；新增底部导航「网络过滤」等入口。

### 新增文件（12 个主源码 + 2 个测试）

`core/engine/ui/`：
- `NodeSnapshot.kt` —— 节点只读快照。**核心决策**：`AccessibilityNodeInfo`
  无法在 JVM 单测中构造、必须成对 recycle、只在回调期有效。不抽象则
  "该不该点这个节点"完全无法测试，而 S1 是四种策略里唯一代替用户操作界面的。
- `NodeRecycler.kt` —— `recycle()` 自 **API 33 起弃用**（框架接管生命周期），
  但 `minSdk=30` 意味着 API 30–32 上不回收是**真实原生内存泄漏**。
  集中做版本分支，而非在调用点 `@Suppress` 后删掉回收调用。
- `UiTreeScanner.kt` —— BFS（非 DFS，因匹配需"浅层优先"），上限 2000 节点防 ANR，
  跨应用节点不展开子树，队列剩余节点必须 drain 回收。
- `UiMatcher.kt` —— 纯逻辑匹配。VIEW_ID > TEXT > DESCRIPTION > COORDINATE。
  viewId 支持短名匹配（`substringAfterLast('/')`），换包名后规则仍可用。
  COORDINATE 不"找最近节点"而是合成虚拟节点 —— 强行就近匹配会把点击目标改到别处。
- `AntiMisclickGate.kt` —— 三重闸门：规则冷却 3s + 节点冷却 5s + 全局节流 400ms。
  成本不对称：漏点=广告没关掉，误点=可能触发付费。有 prune 防记账泄漏。
- `ClickExecutor.kt` —— 三级降级：节点自身 → 向上找可点击祖先（≤5 层）→ 坐标手势。
  "向上找祖先"是关键：广告跳过 TextView 自身 `clickable=false`，响应的是父容器。

`core/repository/S1RuleCache.kt` —— 按包名分组的不可变快照（AtomicReference），

## ⭐ 三个必须记住的设计决策

### 1. `SkipRuleSource` 必须存 `persistedName`（小写），不能用 `enum.name`

```kotlin
enum class SkipRuleSource(val persistedName: String) {
    BUILTIN("builtin"), IMPORTED("imported"), USER("user");
    companion object {
        // 未知值退回 USER（最需保护）
        fun fromName(raw: String?): SkipRuleSource =
            when (raw?.trim()?.lowercase()) {
                NAME_BUILTIN -> BUILTIN; NAME_IMPORTED -> IMPORTED; else -> USER
            }
    }
}
```

理由：迁移的 `DEFAULT 'user'` 与 `SkipRuleEntity.SOURCE_*` 都是**小写**。
用 `enum.name` 会得到 `"BUILTIN"`/`"USER"`，导致 `WHERE source = 'user'` 查不到新数据，
**现象是「规则莫名消失」**。

**约束**：enum 构造参数**不能引用 companion 常量**
（`Companion object of enum class ... is uninitialized here`），必须写字面量。

### 2. 内置导入必须跨来源去重、且只增不改不删

`RuleRepository.mergeBuiltin` 的四条契约（全部有单测锁住）：

- **幂等**：重复启动/重复导入不产生重复规则
- **只增不删**：不删除任何存量规则
- **不改**：用户对规则的改名/停用/删除**不被覆盖**
- **跨来源去重**：`allExistingKeys()` 查 `dao.loadAll()` 全表，
  用户已建同定位值规则时**阻止内置插入**（否则出现重复项同时参与匹配与点击）

`insertAll` 由 `REPLACE` 改 **`IGNORE`** ——
`REPLACE` 会**重置用户停用状态**并**改变行 id**。

业务键 `SkipRuleKey`：`packageName + activityName + targetType + targetValue.lowercase()`，
**不含** `name` / `priority`（因 `UiMatcher` 匹配本身 `ignoreCase`）。

### 3. CONTAINS 误点防护放**规则编写层**，不放 `UiMatcher`

我曾尝试在 `UiMatcher.matchesContains` 加 8 字符候选长度护栏，
**导致既有测试失败**：`given contains rule when node text contains target then matched`
用 12 字正文 "跳过广告，立即观看正片" 断言应命中。

**我判断该既有测试是正确的**（CONTAINS 就该如其名所示地匹配），
因此**完全撤回**护栏实现，把理由写入注释：

> 护栏放匹配器会破坏规则语义，规则页预览会与运行时不一致。

误点防护改由**两层**承担：
1. **规则编写约束** —— `BuiltinSkipRulesAssetTest` 断言
   ①CONTAINS 目标串 ≥ 4 字符 ②不含诱导性词汇（立即/领取/查看/下载/打开/安装/
   购买/下单/抽奖/红包/优惠/开通/授权/同意/允许）
2. **`AntiMisclickGate` 冷却层**（规则 3s / 节点 5s / 全局 400ms）

## 防回归契约（全部在单测中锁住）

- 重复启动/重复导入不产生重复规则（幂等）
- 用户停用的内置规则不被重新导入复活
- 用户对现有规则的改名/修改不被覆盖
- 合并只增不删
- 跨来源去重（用户规则阻止内置插入）
- 内置规则文件不含诱导性词汇、CONTAINS 目标串 ≥ 4 字符、无坐标规则

- v1→v2 迁移保留存量数据与停用状态

# R7（2026-09-19）—— 启动应用半秒延迟

## 用户报告

> "广告拦截关闭成功，但是启动任何应用时存在一个半秒左右的明显延迟"

**注意反馈的性质变化**：这不是"拦截失效"，而是**拦截生效后引入的副作用**。
排查方向完全不同于 R6 —— 这次要找的是"谁在主线程干了重活"。

## 根因（三个叠加来源）

1. **点击在主线程同步执行**。`onAccessibilityEvent` 默认在主线程回调，
   而 `ClickExecutor.execute` 内含 `findByIndex` 全树 BFS 回查 +
   `ACTION_CLICK`/`getParent` IPC，失败时回落 `dispatchGesture`（手势播放约 40ms）。
   单次 50–300ms。
2. **每个相关事件都遍历整树**。已纳管应用启动时内容变化事件数十次，
   每次 `rootProvider()` + `UiTreeScanner.scan()`；500 节点 = 数百次 `getChild` IPC。
3. **`notificationTimeout = 100ms`** 额外引入最多 100ms 延迟。

三者叠加正好是用户感知的"半秒"。

## 修复四项

1. **`EventPreFilter`（新增）** —— 用事件自带 text/desc 做无 IPC 预筛，
   不沾边直接 `Ignored(PRE_FILTERED)` 返回，一次节点读都不做。
2. **点击投递到 `Dispatchers.Default`** —— `performAction`/`getChild` 是 IPC，
   **不受"必须主线程"约束**。新增 `ProcessOutcome.ClickScheduled` / `Deferred`。
3. **`EVENT_TIMEOUT_MS` 100 → 0** —— 及时性换回来，降频职责交给预筛。
4. **Room 启用 WAL** —— `.setJournalMode(WRITE_AHEAD_LOGGING)`。

## ⭐ 核心铁律（R7 最重要的产出）

**预筛只放宽、不收紧。**

预筛一旦比权威实现 `UiMatcher` 严格，就产生"事件被预筛丢弃、永远走不到匹配"的
**静默漏拦**，现象与"规则写错"完全一致，极难排查。

具体推导出的规则：
- 规则集为空 → 放行
- **任何 `VIEW_ID`/`COORDINATE` 型规则 → 整体放行**。
  原因：`AccessibilityEvent` **没有** `viewIdResourceName` 属性
  （那是 `AccessibilityNodeInfo` 才有的），从事件侧根本无法判断 viewId 规则。
  这一条是我写代码时踩出来的真坑（编译期报 `Unresolved reference`）。
- 任何 `REGEX` 型规则 → 整体放行（正则 ≠ 前缀匹配）
- 事件无文本候选 → 放行（信息不足绝不能替权威实现做否决）
- **不做 activity 预筛** —— 纯字符串比较无 IPC 成本，交给 `filterByActivity` 即可

由 `EventPreFilterTest.givenRealWorldSkipTexts_whenMatcherHits_thenPreFilterAlwaysPasses`
强制守护：枚举真实文案，逐条断言「`UiMatcher` 命中 ⇒ 预筛必然放行」。

## 由测试捕获的设计缺陷

我在 `EventPreFilter` 里自实现了 activity 预筛，**它比权威实现更严格**
（class 不同就过滤掉）→ 违反"只放宽"不变式。
测试失败两次才暴露：第一次我误把失败归因于 activity，用"无关内容"当候选；
第二次移除 activity 预筛后仍失败，才发现断言本身有问题。
改用 `"跳过 1"` 使文本匹配成立，才真正隔离出要验证的点。

> **这条是 R7 最有价值的产出 —— 它是测试抓出来的，不是实机抓出来的。**
> 放任不管的话，用户会看到"某些应用又拦不住了"，
> 而排查方向会错误地指向规则文件。

## 诊断扩展（供用户实机核对）

`SkipDiagnosticsState` 新增 `lastCostMs` / `maxCostMs` / `slowEventCount`，
常量 `FRAME_BUDGET_MS = 16L`、`SLOW_EVENT_THRESHOLD_MS = 100L`，派生 `hasFrameDrop`。
规则页诊断卡片新增「单次处理耗时：最近 Nms · 峰值 Mms」。

**`ClickScheduled` 不计入 `totalClicks`** —— 投递 ≠ 点击成功，统计口径不能乐观化。

## 用户请求（前提需要纠正）

> "无障碍权限在离开应用界面一段时间或息屏或切换应用等情况之后系统自动又关闭了，
> 想办法使无障碍权限开启后在手机未关机情况下常驻"

**前提错了，必须先纠正方向**：

**无障碍不存在"常驻"这个状态，因此没有"让它常驻"的实现方式。**
Android 的无障碍是**授权模型**——用户勾选后系统写入
`Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES`，之后**由系统自行决定**
何时连接、何时解绑。**没有任何 API 能让应用要求系统"保持连接"。**

官方 `AccessibilityServiceInfo` 文档对 flags 的原文印证：
> This field represents a set of flags used for **configuring** an AccessibilityService.

关键推论：**服务被解绑时，授权记录依然存在** —— 这正是它能自动重连的原因。

| 用户感知 | 实际状态 | 结论 |
|---|---|---|
| "权限被自动关了" | 授权还在，只是服务实例被解绑 | **不需要重新授权** |
| 真正要解决的 | 断开未被及时发现与呈现 | 做**自愈检测**，不是保活 |

## 明确不做（三条路，都有理由）

1. **前台服务 / AlarmManager / JobScheduler 保活** ——
   对无障碍**完全无效**。它们影响进程优先级，而服务绑定由系统的
   无障碍管理器决定。白耗电，且与 `NoAdAccessibilityService` 原有注释冲突。
2. **adb / Shizuku 写 Settings.Secure** —— 需用户每 12 小时重新授权调试；
   属系统性写操作，影响面超出本应用。
3. **FLAG_REQUEST_ACCESSIBILITY_BUTTON** —— 用户选定"只做常规自愈"。
   且官方明确：`targetSdk > 29` 时运行时设置该 flag **会被忽略**，
   必须写进 XML；部分 ROM 不提供该按钮。

## 用户的三项决策

- 恢复方式 → **只做常规自愈（推荐）**
- 状态可见性 → **如实展示断开，并给出原因（推荐）**
- 触发时机 → **应用回到前台 + 息屏/解锁**（未选开机、网络变化）

## 四项改动

1. **状态模型**：`AccessibilityState` 新增 `lastDisconnectedAtMillis` /
   `disconnectReason`，以及三态区分：
   ```kotlin
   val isDisconnectedButAuthorized: Boolean   // ⭐ 已授权但未连接（可自愈）
       get() = !serviceRunning && serviceEnabledInSettings
   val isNotAuthorized: Boolean
       get() = !serviceRunning && !serviceEnabledInSettings
   ```
   新增 `DisconnectReason` 枚举（SYSTEM_UNBOUND / SERVICE_DESTROYED /
   USER_DISABLED_IN_SETTINGS / UNKNOWN）。
   **诚实性约束**：Android 不提供"解绑原因" API，因此**不做推测**，
   只区分确实观察到的回调路径，其余归 UNKNOWN。

2. **首因优先**：`onUnbind` 与 `onDestroy` 因同一次断开先后触发，
   前者信息更具体。`onDisconnected` 不接受覆盖：
   ```kotlin
   disconnectReason = current.disconnectReason ?: reason   // 不是 reason ?: current
   ```
   断开时刻同理只在**首次**写入。

3. **`AccessibilityWatchdog`**（新增，进程级）——
   SCREEN_ON / USER_PRESENT / BOOT_COMPLETED / ACCESSIBILITY_STATE_CHANGED(API 31+)。
   都是系统广播，不受 Android 8+ 后台限制。在 `Application.onCreate`
   **同步启动**（不能进异步块——广播可能早于初始化完成）。
   Android 14+ 须传 `RECEIVER_NOT_EXPORTED`。
   **刻意不注册 SCREEN_OFF**：息屏瞬间状态无意义。

4. **两层刷新分工 + UI 如实呈现** —— 后台靠 Watchdog 广播；
   前台靠 `HomeScreen` 的 ON_RESUME（覆盖"从设置页返回"，
   此时屏幕既没亮也没解锁、广播不会发）。**两层缺一不可。**
   新增 `DisconnectNotice`：**刻意不用 error 配色**、主按钮是
   "前往设置检查"而非"去开启"，文案明确写"不需要重新授权"。

## ⭐ 由测试捕获的两个缺陷

1. **`onDisconnected` 写成 `reason ?: current`** ——
   等价于"有值就覆盖"，`onDestroy` 依然会盖掉 `onUnbind` 的更具体原因。
   由 `givenAlreadyUnbound_whenOnDestroyCalled_thenDoesNotOverwriteReason` 钉死。

2. **`AccessibilityStateHolder` 直接用 `SystemClock.elapsedRealtime()`，
   导致整个状态机在 JVM 上无法测试** ——
   `android.jar` 是空壳，方法体全是 `throw`，报
   `Method elapsedRealtime in android.os.SystemClock not mocked`。
   **而状态机决定 UI 说"去设置"还是"等一等"，是最不能靠猜的部分**，
   它在修改前完全不可测。
   修正：抽出 `internal var clock: () -> Long = { SystemClock.elapsedRealtime() }`，
   测试注入计数器 → 「已断开多久」的边界
   （刚断开 / 59秒 / 1分 / 59分 / 1小时）才变得可验证。

> 第 2 条是 R8 最有价值的产出。**也是测试逼出来的，不是读代码发现的。**

## 顺带修掉的 UI 逻辑漏洞

`when` 分支里，`isDisconnectedButAuthorized && appSwitchEnabled` 之前会落到
`else`，给用户显示「开启无障碍拦截」——**而它本来就是开着的**。
会误导用户去点一个无意义的按钮。已补显式分支。

同时把硬编码的 `Text("已开启")` 换成 string resource（违反项目规范）。

## 测试的诚实边界

`refreshFromSystemSettings` 依赖 `ContentResolver`，项目**无 Robolectric**，
JVM 拿不到。因此提供 `internal fun seedSettingsFlagForTest(enabled: Boolean)`
验证**由该字段驱动的三态判定**。

**不覆盖**设置读取路径本身——那是 Android 平台行为，由用户实机验证。
已在测试类 KDoc 中如实标注，**不假装覆盖了 `Settings.Secure` 读取**。

# R9（2026-09-19）—— 后台保活：进程存活与自恢复

## 用户请求

> "现在实现一下软件本身的后台常驻避免被意外杀掉，以及软件自拉起处理
> 在非关机情况下被杀掉后需要自启的情况，这个功能需要在设置界面配置可关闭"

## 与 R8 的分工（关键前提）

R8 管**无障碍服务连接层**（系统解绑 → 重连，授权模型内自愈）；
R9 管**应用进程存活层**（进程被杀 → 拉起）。两层互补不冲突：
连接层自愈的前提是进程活着；进程死了必须由进程外机制拉起。
R8 文档中「保活对无障碍无效」的结论依然成立——R9 的保活
**不是**为了让无障碍绑定不断开，而是防止进程死亡这种更彻底的失效。

## 用户决策（RESOLVE 确认）

- 开关结构 → **两个独立开关**：「后台保活」（新）+「开机自启动」（假开关接真）
- 电池优化 → **加豁免直达入口**

## 核心设计：三层恢复链

| 层 | 触发点 | 延迟 | 原理 |
|---|---|---|---|
| ① 粘性重启 | START_STICKY 被杀后系统自行重启 | 秒级 | 系统发起的重启豁免后台启动限制，onStartCommand 收 null intent |
| ② 心跳闹钟 | 15 分钟一次性闹钟链（setAndAllowWhileIdle 非精确） | ≤15 分钟 | PendingIntent 系统侧持有，**进程死亡不清除闹钟** |
| ③ 系统广播 | BOOT_COMPLETED + MY_PACKAGE_REPLACED | 重启/更新后 | 官方 FGS 后台启动豁免；更新清空闹钟后由它重建链条 |

关键决策：
- **心跳失败也必须重排**（TRY_START_AND_RESCHEDULE 字面契约）——
  一次性闹钟不重排即断链，失败 → 下次心跳重试是唯一自愈路径
- **镜像乐观策略**：粘性重启时镜像 null（未同步）→ 乐观恢复；
  唯一硬约束是明确 false 必须停止（「关不掉」bug 的唯一入口）
- **接收器读 DataStore 权威值**而非内存镜像（BOOT 路径进程刚拉起，
  镜像必为 null，读权威值避免启动竞态）
- **非精确闹钟**（setAndAllowWhileIdle）：精确闹钟 13+ 需
  SCHEDULE_EXACT_ALARM 且默认被拒；15 分钟 > Doze 9 分钟合并窗口
- **ELAPSED_REALTIME_WAKEUP** 单调时钟：不受改时间/时区影响
- **闹钟 PendingIntent 用显式 Intent**，不进 manifest filter，无第三方触发面
- **刻意不在 Service.onDestroy 取消闹钟**（心跳必须比服务活得久）
- **FGS 类型用 specialUse**：Android 15 BOOT 限制只放行 6 类 FGS，
  specialUse 在白名单内；manifest 带 PROPERTY_SPECIAL_USE_FGS_SUBTYPE
- **通知渠道 IMPORTANCE_LOW**：常驻通知静默；13+ 通知权限拒绝
  不阻断保活（服务照常跑，仅通知不可见）

## 双开关门控语义

- 保活开关：管「运行期不被杀 + 被杀自恢复」（粘性重启/心跳/更新后恢复只看它）
- 自启开关：只管「重启后恢复保活」；BOOT 门控 = `keepAlive && autostart`
- **更新后恢复（MY_PACKAGE_REPLACED）只看保活开关**：更新是用户主动行为
- 设置页副标题约束：自启开关写「设备重启后恢复后台保活」，
  **不能写「恢复拦截」**（无障碍重启后由系统授权模型自动重连，与开关无关）

## 诚实边界

**force-stop 后任何应用都无法自启**（Android 安全设计），三层恢复链
覆盖的是系统回收场景，文档与 UI 均不夸大。

## 新增/修改文件

新增（`core/service/keepalive/`）：
- `KeepAlivePolicy.kt` —— 纯决策层（internal object，JVM 可测），
  四个决策函数 + 四个枚举，锁死两条不变式
- `KeepAliveRuntime.kt` —— 设置三态镜像（@Volatile，null=未同步）
- `KeepAliveScheduler.kt` —— 闹钟排期/取消，`HEARTBEAT_INTERVAL_MS = 15 * 60_000L`

- `res/drawable/ic_notification.xml` —— 白色盾牌（通知小图标须纯 alpha）

  （独立 Flow，默认 false）
